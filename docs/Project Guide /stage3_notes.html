壹 · Section I

数据集总览

The opening statement — show the data's ID card

这一节的角色是"开场陈述"——快速把数据的"身份证"亮出来。

5 个关键信息

项目关键内容
数据来源来自腾讯广告真实日志(real-world logs,不是合成数据)
数据状态完全脱敏(fully anonymized)
规模100 万样本(学术赛道) · 工业赛道 200 万
结构120 列,扁平(flat)
类别分 6 大类

"真实日志" vs 合成数据

真实日志 · 业务系统实际产生的数据 — 包含真实的长尾、噪声、异常值;在它上面验证的方法有工业意义

合成数据 · 程序伪造的"假用户"数据 — 干净但工业相关性弱

📝 写 report 时,可以强调 "real-world industrial logs" 而不是 "simulated data"——这本身就是加分点。

"扁平" vs "嵌套"结构

扁平结构 · 每行就是一行,所有列并排放着 — 用 CSV 就能存,加载快

嵌套结构 · 字段里藏着复杂结构 — 像 JSON 一样有层级

腾讯选了扁平结构。代价是:序列特征(本来是一串值)在扁平表里得存成字符串,代码读取时再 split 成数组。

规模:100 万到底算大算小?

规模例子
几万学术玩具数据集(MovieLens-100K)
几十万中等规模(MovieLens-1M)
100 万中大规模 · 单卡 GPU 一天能跑完
几亿工业级(Criteo 4.5 亿)

学术赛道把规模压到 100 万,意味着方法本身的创新而非工程能力是竞争点——单卡能跑得动,鼓励快速迭代。

隐私保护机制

"完全脱敏"具体怎么做的?

  • 所有稀疏特征都是匿名整数 ID
  • 所有稠密特征都是固定长度 float 向量
  • 没有原始内容(无文字、图片、URL)
  • 没有 PII(个人可识别信息)

关键约束:不能用预训练 LLM/CV 模型做特征工程。

→ 这反而让方法论更纯粹:所有创新必须发生在架构设计、注意力机制、训练策略上,而不是"借力外部预训练模型作弊"。

贰 · Section II

120 列详解

Six categories, each with its own personality

3 种数据类型

这一节会反复出现 3 种类型,先搞清楚:

类型说明例子
int64 / int32单个整数user_id = 87234691
list<int64>一串整数seq = [556712, 887341, 661203]
list<float>一串小数dense = [10.5, 20.0, 15.5]

6 大类的详细对照

类别 1

ID & Label

5 列 · int64/int32

元数据 + 监督信号:user_id, item_id, label_type, label_time, timestamp。不是模型输入特征,而是身份证 + 答案。

类别 2

User Int Features

46 列 · int64 / list<int64>

用户离散特征(年龄、性别、兴趣标签等)。35 标量 + 11 多值。

类别 3 ⭐

User Dense Features

10 列 · list<float>

2 列预训练 embedding(SUM, LMF4Ads)+ 8 列与 Int 列对齐的 (key, value) 对。

类别 4

Item Int Features

14 列 · int64 / list<int64>

商品离散特征(类目、类型、多标签)。13 标量 + 1 多值。

类别 5(空)

Item Dense Features

0 列

商品没有稠密特征。这是个潜在的 contribution 空间——可以人工造一些(点击率、热度等)。

类别 6

Domain Sequence Features

45 列 · list<int64>

4 个行为域的序列特征。占总数 38%,是数据集的"主战场"。下一节展开。

关键概念:"标量" vs "多值"

标量(scalar) · 每条样本一个数 · 例:user_age = 30

多值(multi-value) · 每条样本一串数 · 例:user_tags = [12, 89, 156, 203](用户被打了多个兴趣标签)

多值 ≠ 序列

多值(多标签)序列(行为时间线)
顺序无意义有意义(时间先后)
例子兴趣标签 [体育, 科技, 美食]浏览历史 [A, B, C, D]
用途描述用户的"画像"描述用户的"演化"

⭐ User Dense 的对齐结构(本节精华)

10 列 User Dense 拆开看:

前 2 列:SUM 和 LMF4Ads

这两个名字看起来很专业,其实就是两个预先训好的向量——腾讯内部用其他大模型预训练好的"用户画像向量",直接送给参赛者使用。

→ 这是腾讯白送的预训练 embedding,可以直接拿来用,不用自己再训。

后 8 列:与 Int 列逐元素对齐(本节最关键概念)

user_int_feats_62: [1, 2, 3] # 实体 ID(类目 ID)
user_dense_feats_62: [10.5, 20.0, 15.5] # 对应的统计量(停留时长)

这两列逐元素对齐:

位置int 值(标签)dense 值(数值)含义
第 1 个类目 110.5 秒用户在类目 1停留 10.5 秒
第 2 个类目 220.0 秒用户在类目 2停留 20.0 秒
第 3 个类目 315.5 秒用户在类目 3停留 15.5 秒

这是 (key, value) 对的存储方式。

单独存"类目"或单独存"时长"都不完整;对齐结构 = 同时保留两种信息,而且关联起来。

→ 它揭示了一种重要的特征建模思想:用 dense 给 sparse 做"权重"。

叁 · Section III

4 个行为域

The most complex part of the dataset

4 个域的列范围分布

域名 列名范围 列数
Domain A domain_a_seq_{38–46} 9
Domain B domain_b_seq_{67–79, 88} 14
Domain C domain_c_seq_{27–37, 47} 12
Domain D domain_d_seq_{17–26} 10

9 + 14 + 12 + 10 = 45 列 ✅(对得上 Domain Sequence 总数)

注意 B 和 C 的"不连续":Domain B 占 67–79 + 第 88 列;Domain C 占 27–37 + 第 47 列。

→ 4 个域分散在 120 列的不同位置。dataset.py 必须用列名映射把散乱的列归类到 4 个域里(seq_domains = ["a", "b", "c", "d"])。

4 个域可能代表什么?

腾讯没明说,可能的含义:

维度4 个域可能的含义
行为类型曝光 / 点击 / 收藏 / 转化
产品场景微信 / QQ / 腾讯视频 / 腾讯新闻
内容类型视频广告 / 图文广告 / Banner

"语义不可知"反而是学术优点:你设计的方法对未知语义的多域数据都适用,而不是"针对腾讯数据特调"。写 report 时只写 "4 heterogeneous behavior domains",不要瞎猜具体含义。

域内多列的对齐结构

每个域内 9~14 列逐元素对齐,共同描述同一段行为序列的不同侧面:

domain_a_seq_38: [1001, 1024, 2055, 3088] # 商品 ID 序列
domain_a_seq_39: [10, 10, 25, 30] # 这些商品的类目 ID
domain_a_seq_40: [1672531200, ...] # 对应的时间戳

把上面的列放在一起,横着读:

时间位置商品 ID类目 ID时间戳
第 1 次行为1001101672531200
第 2 次行为102410...
第 3 次行为205525...
第 4 次行为308830...

→ 一行就是这位用户在 Domain A 里的一次完整行为。

时间桶机制(time bucketization)

原始时间戳的问题

domain_a_seq_40 = [1672531200, 1672617600, 1672704000, ...]
                    ↑           ↑           ↑
                    Unix 时间戳(秒,从 1970 年算起)

数字本身没意义。直接喂给模型不行(数太大,数值范围乱)。

解决方案:65 个时间桶

把"两次行为之间的时间差"分成 65 个桶:

桶 0:  0~5 秒       ← "刚刚发生"
桶 1:  5~10 秒
桶 2:  10~30 秒
...
桶 30: 1 小时左右
...
桶 64: 接近 1 年    ← "很久以前"

→ 时间戳被转成桶 ID(0~64 之间的整数)。

原因说明
数值范围统一都变成小整数,适合 embedding
粗粒度更稳模型不关心"4 秒前 vs 5 秒前",但关心"几分钟前 vs 几个月前"
桶可以学 embedding每个桶变成一个向量,模型学"刚刚"和"很久以前"的语义差别

📁 代码定位:dataset.py · BUCKET_BOUNDARIES(line 110-121)。这是一个常量列表,定义了 65 个桶的边界。

这是个改进点:桶的边界是可调参数。你可以增加桶数、调整边界分布、用对数刻度——这是个简单但可能有效的改进方向,尤其针对"baseline 在长序列上效果差"。

肆 · Section IV

两种数据格式

Don't confuse them — same data, different packaging

Demo 数据(7 列嵌套 struct)和正式比赛数据(120 列扁平)是同一份数据的两种打包方式。

底层信息一样,代码处理方式不同。

格式 1 · Demo 格式(7 列嵌套)

Hugging Face 上的 TAAC2026/data_sample_1000,只有 7 列:

user_id        (string)
item_id        (int64)
timestamp      (int64)
label          ─ array of struct: [{action_time, action_type}]
user_feature   ─ array of struct: [{feature_id, value_type, int_value, ...}]
item_feature   ─ array of struct(同上)
seq_feature    ─ struct, 包含 action_seq, content_seq, item_seq

→ 每一列里藏着复杂的嵌套结构。

格式 2 · 正式格式(120 列扁平)

user_id, item_id, label_type, label_time, timestamp,
user_int_feats_1, ..., user_int_feats_46,
user_dense_feats_56, ..., user_dense_feats_91,
item_int_feats_92, ..., item_int_feats_119,
domain_a_seq_38, ..., domain_d_seq_26

→ 把上面的嵌套结构全部展平成 120 个独立列。

为什么有两种?

格式优势用途
Demo结构紧凑,人读起来好懂本地开发、调试、写代码
正式列式存储,加载快真正训练时用

实操陷阱:

  • 写代码时:用 Demo 数据(1000 行,本地能跑)调试逻辑
  • 训练时:切换到正式格式(100 万行)
  • 关键:你的 dataset.py 代码必须能处理"扁平 120 列"格式 — 别在 Demo 数据上写完代码,切到正式数据时才发现读不进去

3 个最关键的 insight

洞察启发
(key, value) 对齐结构User Dense 不是"独立的 10 列",而是和 Int 列绑定的(key=ID, value=统计量)。这种结构本身值得在 report 里点出

自检四问

Q1 User Dense 中的"对齐结构"和 Domain Sequence 内部的"多列对齐"有什么共同点和不同点?

共同点:都是"多个列逐元素对齐",共同描述同一组实体的不同属性。

不同点:

  • User Dense 对齐:描述"静态用户画像的(类目, 统计量)对" — 没有时间顺序
  • Domain Seq 对齐:描述"动态行为序列的(商品, 类目, 时间戳, ...)对" — 有时间顺序

→ 同样的"对齐"机制,在静态和动态两个层面都被使用了——这是腾讯 schema 设计的一致性。

Q2 为什么时间戳要转成"桶 ID"而不是直接喂给模型?

3 个原因:

  • 数值范围:Unix 时间戳是几十亿的大数,直接喂会把数值范围搞乱
  • 粒度问题:模型关心"几分钟前 vs 几个月前",不关心"1672531200 vs 1672531205"
  • 可学习性:转成桶 ID 后,每个桶可以学 embedding,语义化"刚刚"和"很久以前"

→ 这个技巧叫 time bucketization,是处理时间信号的标准做法。

Q3 Demo 格式(7 列)和正式格式(120 列)是同一份数据,为什么要做两份?

不是"两份不同数据",是同一份数据的两种打包方式:

  • Demo 格式:嵌套 struct,人读起来好懂,适合本地调试(只有 1000 行)
  • 正式格式:扁平 120 列,列式存储加载快,适合大规模训练(100 万行)

⚠️ 实操陷阱:在 Demo 上写完的代码,如果直接切到正式数据,可能因为"格式不一样"而读不进去。你的 dataset.py 必须处理的是扁平 120 列格式,Demo 只是辅助。

Q4 为什么 "Item Dense = 0 列" 是个值得关注的设计?

商品在这份数据里只通过离散 ID 来表达,没有连续值的"画像"或"统计指标"。这意味着:

  • 模型必须完全靠 item embedding 来学习商品的"含义"
  • 反过来,这给你们留了一个 contribution 空间——可以人工造一些商品的统计特征(比如点击率、出现频次),作为新的 dense 列加进去

→ "空白"本身就是一个机会。
