🎯 30 秒电梯演讲

如果有人突然问"你们这个项目在做什么?",照这段讲

我们参加的是腾讯 × KDD Cup 2026 广告算法大赛。这个比赛要解决一个工业界长期存在的问题:推荐系统里有两类 AI 模型——一类擅长处理用户和商品的静态属性,另一类擅长处理用户的行为时间线——它们一直没法很好地融合。

我们的任务是基于一份脱敏后的腾讯广告日志(100 万条样本、120 个特征列、4 个行为域),设计一个能把两类信息深度融合的模型,来预测"用户会不会点击某个广告"。赛方提供了一个叫 PCVRHyFormer 的官方 baseline,我们的工作是在它的基础上做改进,然后把整个研究过程写成一篇 9 页的 NeurIPS 风格 report 作为课程项目交付。

🤔 为什么有这个比赛?

背景 — 推荐系统两条技术路线的分裂史

过去 20 年,工业推荐系统沿着两条互不相通的技术路线发展:

路线 1 · 特征交互模型

Feature Interaction Models

擅长建模静态特征之间的交叉,比如"年龄 × 商品类目 × 时段"。

代表模型演进:

FM (2010) → Wide & Deep (2016) → DeepFM (2017) → DCN/DCNv2 (2017/2020) → xDeepFM (2018) → AutoInt (2019) → FinalMLP (2023) → Wukong (2024)

路线 2 · 序列建模模型

Sequential Recommendation Models

擅长建模用户的行为时间线,捕捉兴趣演化。

代表模型演进:

GRU4Rec (2015) → DIN (2018) → DIEN (2019) → SASRec (2018) → BERT4Rec (2019) → BST (2019) → TWIN/TWIN-V2 (2023/2024) → HSTU (2024)

核心矛盾 · The Core Conflict

这两条路线长期独立发展,在工业系统里造成 4 个具体问题:

问题英文术语具体表现
跨范式交互浅 Shallow cross-paradigm interaction 两套模型的输出通常只是简单拼接,没有深度融合
优化目标不一致 Inconsistent optimization objectives 序列模型常用对比学习,特征模型用 BCE,目标对不齐
扩展性受限 Limited scalability 两个分支各自 scale,模型变大但效果未必提升
硬件复杂度高 Increasing hardware complexity 两套不同的计算图、优化器配置、部署方式
🎯 比赛的核心命题
设计一个统一的、可堆叠的模型块(Unified Block),把这两类信息无缝融合,提升 CTR 预测的准确度。 同时鼓励探索推荐系统的 Scaling Law(参数量 / 数据量 / 算力 vs 性能)。 algo_qq_com.pdf

任务名 · Task Name

CTR 预测 · Click-Through Rate Prediction — 工业界最经典的二分类任务之一。

输入 → 输出

输入 Input
用户 + 候选广告 + 用户在 4 个域的行为序列
→
输出 Output
[0, 1] 之间的概率,代表"会不会点击"

四个层次的难点 · Four Layers of Difficulty

难点 1 · 特征极度稀疏且高维
用户 ID 上亿、商品 ID 几百万,不能用 one-hot,必须学 embedding。但 embedding table 一大显存就爆。
model.py · _make_seq_embs · emb_skip_threshold
难点 2 · 行为序列又长又异构
用户有几百到几千次历史行为,而且分散在 4 个不同的域(domain_a/b/c/d)。怎么融合是开放问题。
dataset.py · seq_domains
难点 3 · 静态特征和序列特征的"统一"
传统做法:序列编码器 → 一个向量,静态特征 → 一个向量,拼起来送分类器。信息损失严重。 比赛要求探索更深入的融合方式。
model.py · MultiSeqHyFormerBlock
难点 4 · 推理延迟限制
模型不能太大。学术赛道有固定的延迟预算,超过就直接判废,不管 AUC 多高。这意味着不能像 LLM 那样无脑堆参数。
algo_qq_com.pdf

📐 评估方式

主指标 · Primary Metric

AUC of ROC(越高越好)

衡量模型给"会点击"的样本排在"不点击"样本前面的能力。AUC = 0.5 是随机猜,1.0 是完美。

硬约束 · Hard Constraint

推理延迟限制

超过预算的提交直接作废。具体数值赛方动态公布,你们 report 里只需说"subject to the latency constraint"即可。

类别列数类型含义来源

⭐ 重点解读:User Dense 的对齐结构

User Dense 中有 8 列(fid 62-66, 89-91)是和 User Int 中同 fid 的列逐元素对齐的。

user_int_feats_62:   [1, 2, 3]           # 实体 ID(类目 ID)
user_dense_feats_62: [10.5, 20, 15.5]   # 对应的统计量(停留时长 / 概率)

含义:(key, value) 配对结构 — 用户对类目 1 停留 10.5 秒、对类目 2 停留 20 秒...

💡 4 个域代表什么?
赛方没明说,根据推荐系统常识可能是:
  • 不同的行为类型(曝光 / 点击 / 收藏 / 转化)
  • 不同的产品场景(微信 / QQ / 腾讯视频 / 腾讯新闻)
  • 不同的内容类型(视频广告 / 图文广告 / Banner)

不知道具体语义没关系 — 模型不需要知道,你们也不需要。只需要知道有 4 路独立序列,需要融合机制。

每个域内多列序列代表什么?

每个域内的多列逐元素对齐,共同描述同一段行为序列的不同侧面:

domain_a_seq_38: [1001, 1024, 2055, 3088]   # 商品 ID 序列
domain_a_seq_39: [10, 10, 25, 30]            # 这些商品的类目 ID
domain_a_seq_40: [1672531200, ...]           # 对应的时间戳

其中,时间戳列会被转成时间桶 ID(共 65 个桶,边界从 5 秒到 1 年): dataset.py · BUCKET_BOUNDARIES (line 110-121)

💡 三大核心概念

理解 PCVRHyFormer 必须先理解这三个术语

1. NS Tokens
Non-Sequence Tokens · 非序列令牌

把多字段稀疏特征变成 Transformer 友好的 token。

所有 user/item 离散特征分组压缩成一个或几个 d_model 维向量,这样它们就能像"词"一样进入 Transformer。

两种变种:
• GroupNSTokenizer — 每组 → 1 个 token(语义化)
• RankMixerNSTokenizer — 拼起来切成 N 个 token(默认)

model.py · GroupNSTokenizer (line 988) / RankMixerNSTokenizer (line 1070)
2. Sequence Tokens
序列令牌

4 个域的行为序列变成 token 序列。

每个域(seq_a/b/c/d)独立处理:

  • 每列做 embedding
  • 同一时间步沿特征维度 concat
  • Linear + LayerNorm 投影到 d_model
  • 加上 65 桶时间桶 embedding
model.py · _embed_seq_domain (line 1544)
3. Q Tokens
Query Tokens · 查询令牌

给每个序列分配的"读取头"。

Query 不直接接收序列,而是主动去序列里查找:

Q_i = FFN_i(Concat(NS_tokens, MeanPool(Seq_i)))

Query 同时包含全局特征信息(NS)和该序列的全局摘要 — 这是融合的入口。

model.py · MultiSeqQueryGenerator (line 415)

三者的关系 · How they work together

用比喻:模型在做"广告推荐决策",大脑里有 3 类信息:

  • NS Tokens = "桌上的档案夹" — 静态画像
  • Sequence Tokens = "旁边的监控录像" — 动态行为
  • Q Tokens = "决策者的若干个'问题'" — 主动去档案夹和录像里查答案

🔄 完整数据流

从原始 batch 到 logit 输出的全过程

  1. Step 1 · 输入解包

    ModelInput 包含 7 个张量:user_int_feats, item_int_feats, user_dense_feats, item_dense_feats, seq_data, seq_lens, seq_time_buckets

    model.py · class ModelInput (line 11)

  2. Step 2 · NS Tokens 构建

    user_ns = user_ns_tokenizer(user_int_feats) → (B, num_user_ns, D)
    + 用户 dense 特征通过 MLP 投影成 1 个额外 token
    + item ns + (可选) item dense token
    → 拼接得到 ns_tokens (B, num_ns, D)

    model.py · forward step 1 (line 1637)

  3. Step 3 · 序列 Token 化

    每个域独立处理:embedding → concat → 投影 → 加时间桶
    得到 seq_tokens_list = [(B, L_1, D), (B, L_2, D), (B, L_3, D), (B, L_4, D)]

    model.py · _embed_seq_domain (line 1544)

  4. Step 4 · Query 生成

    q_tokens_list = query_generator(ns_tokens, seq_tokens_list, seq_masks)
    每个域生成 num_queries 个 query token,作为该域的"读取头"

    model.py · MultiSeqQueryGenerator.forward (line 456)

  5. Step 5 · HyFormer Block 堆叠(核心 ⭐)

    堆 num_hyformer_blocks=2 层。每层 5 步:

    1. Sequence Evolution — 每域独立跑 SeqEncoder(自注意力)
    2. Query Decoding — Q ← CrossAttn(Q, Seq) 读取信息
    3. Token Fusion — Concat([Q_1, Q_2, Q_3, Q_4, NS])
    4. Query Boosting — RankMixerBlock(融合后的所有 token)← 这就是"统一"的实现!
    5. Split — 拆回 per-domain Q + 更新后的 NS
    model.py · MultiSeqHyFormerBlock (line 850)

  6. Step 6 · 输出投影 + 分类

    所有 Q tokens 拼接 → MLP 投影到 D 维 → Classifier (Linear + LayerNorm + SiLU + Dropout + Linear) → logit

    model.py · output_proj + clsfier (line 1416-1431)

  7. Step 7 · Loss 计算

    BCEWithLogitsLoss(默认)或 Focal Loss(alpha=0.1, gamma=2.0,可选)
    反向传播 → 双优化器更新参数

    trainer.py · _train_step (line 402) · utils.py · sigmoid_focal_loss (line 260)

特征类别列数分析重点

🔬 推荐分析方法

对每一列特征都建议从以下维度切入:

第一步 · 单列基础统计

分析维度方法能推断什么
Cardinality 基数 df[col].nunique() 2-5 → 性别/婚姻类;~100 → 年龄/职业;100w+ → 用户 ID 类
Distribution 分布 直方图、箱线图 钟形 → 连续量(年龄、价格);长尾 → ID 类;均匀 → 类别码
Sparsity 稀疏率 缺失值/默认值占比 高稀疏 → 可选字段(如职业、学历)
List 长度 对 list<int64> 算长度分布 长度 1-5 → 兴趣标签集;长度 100+ → 行为序列
取值范围 .min(), .max(), quantiles 0-7 → 星期;0-23 → 小时;0-100 → 年龄

第二步 · 与 Label 的关联(找出"哪些特征预测 CTR 最有用")

方法用途
Mutual Information sklearn.feature_selection.mutual_info_classif 量化每列对 label 的预测信息量
分组 CTR 差异 把 feature 按值分组,看每组的 click rate 差异(高方差 → 高判别力)
WOE / IV (Information Value) 金融/风控领域的标准指标,对二分类问题非常有效

第三步 · 跨列关联(找出"哪些特征应该聚一起")

方法用途
Cramér's V(类别 vs 类别) 衡量两个离散特征的关联强度;高关联 → 可能是同一概念的不同视角
Pearson / Spearman(连续 vs 连续) 看 user_dense 内部哪些列高相关
Hierarchical Clustering 把高相关的特征聚到一棵树里,直接看出"语义相近的特征族"
(key, value) 对齐对的关联 验证 feats_62-66, 89-91 的 dense 值是否对应该 key 的统计量(如点击率、停留时长)

第四步 · 4 个 Domain 的差异分析(关键!)

序列长度对比

统计每个 domain 的平均序列长度分布:

  • 短(几十) → 可能是转化/购买行为
  • 中(几百) → 可能是点击行为
  • 长(几千) → 可能是曝光行为

ID 重叠分析

看 4 个 domain 的 item ID 是否共享 vocab:

  • 共享 → 同一 item space,行为类型不同
  • 独立 → 不同产品场景(如不同 APP)

列结构对比

每个 domain 的列数不同(9/14/12/10),看每列vocab size 和分布:

  • 第一列大 vocab → 主 ID(item_id)
  • 后续列小 vocab → side info(类目、动作类型)

时间分布

看每个 domain 的时间戳列分布:

  • 近期密集 → 可能是实时行为
  • 均匀 → 可能是历史归档

❓ 常见困惑 FAQ

Q1 · 比赛排名和课程分数有关系吗?
几乎没关系。课程要求是"做一个 Original Project",不是"拿比赛冠军"。即使你们 AUC 不高,只要 report 写得清晰、方法有想法、实验有逻辑,课程分数照样很高。反过来,AUC 很高但 report 写得差,课程分数也不会好。

→ 精力应该放在 report 上,不是榜单上。
Q2 · 为什么有 demo 数据(嵌套)和正式数据(扁平)两种?
同一份数据,两种打包方式:

• Demo 数据 = 公开预览样本,人人能下载,目的是让你写代码、看格式
• 正式数据 = 比赛平台的真正训练集,只有报名队伍能用

Demo 用嵌套 struct 是因为方便人类阅读;正式数据用扁平 120 列是因为方便代码批量处理。
Q3 · "PCVRHyFormer 是 baseline 不是我们的模型" — 这意味着什么?
意味着 report 里必须诚实标注:

• "We use the official baseline PCVRHyFormer..." → 这是腾讯写的
• "We modified the X module by..." → 这是你们写的

把整个 PCVRHyFormer 当成"Our Method"是严重的学术不端。只有你们对它做的修改,才算你们的 contribution。
Q4 · NS Tokens、Q Tokens、Sequence Tokens 到底分别是什么?
想象模型在做"广告推荐决策",大脑里有 3 类信息:

• NS Tokens = "桌上的档案夹"(用户和商品的画像信息,静态的)
• Sequence Tokens = "旁边播放的监控录像"(用户最近做了什么,按时间)
• Q Tokens = "决策者的若干个'问题'",主动去档案夹和录像里查找答案

最后用 Q Tokens 收集到的答案做决策。
Q5 · 为什么模型这么复杂?直接 MLP 不行吗?
直接 MLP 可以,但 AUC 会低很多。复杂的原因:

• 100 万样本 + 几千万级 ID → 直接学就过拟合
• 4 路异构序列 → 简单平均会丢信息
• 静态 + 动态融合 → 简单拼接信息损失大

工业级推荐系统的复杂度都是必要的,每个模块都是为了解决一个具体问题。
Q6 · 学术赛道、工业赛道、Phase 1/2/3 是什么?
• 学术 vs 工业赛道:两个独立的比赛。学术赛道仅限学生,数据 100 万;工业赛道所有人,数据 200 万。你们参加学术赛道。

• Phase 1 / 2 / 3:比赛三轮,每轮换数据、扩规模。你们的课程截止前 Phase 1 还没结束,所以不影响。
Q7 · 延迟限制为什么重要?
腾讯广告投放是实时的 — 用户打开 APP 那一刻,系统必须在几毫秒内决定展示哪个广告。所以模型再准,如果太慢也没法上线。

比赛模拟了这个工业约束:超过预算的提交直接判废。这告诉你 report 里要包含 latency analysis(延迟分析)— 不仅报 AUC,还要报推理时间。
Q8 · 5 天写 9 页 NeurIPS 论文来得及吗?
来得及,但必须从今天就开始动笔。

• Section 1, 2, 3, 4.1 不依赖队友的工作,可以现在就开始(占 4-5 页)
• Section 4.2 + 5 等队友给数据后再写(占 3-4 页)
• Section 6 + References 最后整合

建议:今天写 Intro + Dataset + Baseline 的初稿,明天写 Related Work,后天等队友数据,最后两天写 Method + Experiments + 整合 + 校对。
