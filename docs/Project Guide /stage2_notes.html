核心矛盾:分裂造成的 4 个工业痛点

这是这一节最有价值的内容——它是 report Introduction 第二段的直接素材。

痛点 #1

跨范式交互浅

Shallow cross-paradigm interaction

两类模型的输出最后只是简单拼接,没有真正交流——两个翻译员各翻一段话给老板,但他俩之间不互相讨论。

痛点 #2

优化目标不一致

Inconsistent optimization objectives

序列模型常用对比学习,特征模型用 BCE 损失——两个学习方向不同,强行拼接像让长跑选手和举重选手做同一套训练。

痛点 #3

扩展性受限

Limited scalability

LLM 时代有 Scaling Law(变大就变好),推荐系统没有这性质——两个分支各自变大都很快饱和,吃不到 GPU 红利。

痛点 #4

硬件复杂度高

Increasing hardware complexity

两套不同的计算图、优化器、部署方式——升级、调试、出 bug 都要在两个世界里来回跳,运维很贵。

比赛的核心命题(直接可写进 report)

"设计一个统一的、可堆叠的模型块(Unified Block),把这两类信息无缝融合,提升 CTR 预测的准确度。同时鼓励探索推荐系统的 Scaling Law。"
关键词含义为什么重要
Unified Block能同时吃静态+序列的"模块"这是 PCVRHyFormer 的设计哲学
可堆叠像 Transformer 层一样堆 N 层对应 baseline 的 num_hyformer_blocks=2
Scaling Law越大越好的规律暗示腾讯希望大家探索更大模型(但要顾延迟)

贰 · Sub-Section II

技术任务定义

From abstract pain to a computable, scorable task

这一节把上一节的抽象痛点包装成具体的可计算任务。如果上一节是新闻稿,这一节就是项目立项书——任务叫什么、给什么、要什么、难在哪。

① 任务名:CTR 预测

任务全名CTR = Click-Through Rate(点击通过率)
任务类型二分类 · Binary Classification
答案空间只有两个选项:点 / 不点
地位互联网广告业的核心算法 · 学术界 15 年论文都为它服务

二分类 · 答案只有两个 · 例:这封邮件是垃圾邮件吗?这个广告会被点吗?

多分类 · 多个选项 · 例:这张图是猫/狗/兔子?

回归 · 一个连续数字 · 例:这套房子值多少钱?

② 输入 → 输出

输入用户 + 候选广告 + 用户在 4 个域的行为序列(就是阶段一讲的 120 列)
输出[0, 1] 之间的概率,代表"会不会点击"
监督信号真实 label(0/1):每条样本都标注了实际有没有被点

为什么不直接输出 0/1?

  • 概率支持排序——广告系统拿到所有候选的概率后,按概率排序,把最有可能被点的排在前面展示
  • 训练上更稳——损失函数(BCE/Focal Loss)基于概率,这是行业标准做法

📁 文件追踪:这一步的逻辑写在 model.py 里的 clsfier 模块。

③ 四个层次的难点

这是这一节的核心——告诉你为什么这件事不能简单地用一个 MLP 解决。

1 特征极度稀疏且高维 High-dimensional sparsity

"高维" = 特征种类太多;"稀疏" = 每条样本里大部分特征都是 0 或缺失。

具体场景:用户 ID 上亿、商品 ID 几百万。每条样本里只有 1 个用户 ID 和 1 个商品 ID,但理论上的可能取值上亿。

One-hot 不可行:用户 ID 10 亿个 → one-hot 向量长 10 亿 → 100 万样本要 1015 个数字。

解决方案 Embedding:每个 ID 对应一个 64 维的稠密向量,让模型自己学。但 1 亿 × 64 ≈ 25 GB 显存,普通 GPU 也吃不消。

📁 baseline 用 emb_skip_threshold=1000000:vocab 超过 100 万的特征跳过 embedding,这是工程妥协。

2 行为序列又长又异构 Long & heterogeneous sequences

"长":用户有几百到几千次历史行为。baseline 截断长度:Domain a/b 是 256,c/d 是 512——比一句话的 token 数还长。Transformer 处理长序列有 O(L²) 复杂度,序列翻倍计算量变 4 倍。

"异构" = heterogeneous,4 个域的行为来自完全不同的场景——频率不同、含义不同、字段也不同。

融合方式是开放问题

方法思路缺点
简单拼接4 域各自编码,最后拼成长向量浅融合,无交流
共享编码器4 域用同一个 Transformer抹掉域间差异
Cross attention让 4 域互相看计算爆炸
Query Tokenbaseline 用的方法 ⭐你们要研究的

📁 dataset.py · seq_domains:每个域独立处理后再交给模型融合。

3 静态特征和序列特征的"统一" Static-sequential fusion

这是上一节"痛点 #1(浅融合)"的具体技术版本。

传统做法:序列编码器 → 一个向量,静态特征 → 一个向量,拼起来送分类器——两个分支整个学习过程互相不知道对方在干嘛。

具体例子 · Concrete Example

健身用户的故事

静态画像:30 岁、男、北京、IT 行业
最近序列:看了健身器材 → 运动鞋 → 蛋白粉

浅融合:静态分支学到"IT 男爱看科技产品",序列分支学到"最近关注健身"——两个独立结论。

深度融合的洞察:"30 岁北京 IT 男 + 最近关注健身 = 新晋健身爱好者,需要入门款而非专业款"——这种"组合后才出现的洞察",浅融合根本捞不到。

📁 PCVRHyFormer 的解决方案:MultiSeqHyFormerBlock——每一层都做 4 步操作,让两类信息在每一层互相打交道。

4 推理延迟限制 Inference latency budget

训练 ≠ 推理:

阶段在做什么时间敏感吗
训练在历史数据上反复学习不敏感(慢一点没事)
推理给当下请求做预测极其敏感

工业硬约束:单次请求 < 50 ms(整个链路),模型本身 < 20 ms。

这给你们的"指南针":

改动方向延迟影响
把 num_hyformer_blocks 从 2 加到 8⚠️ 计算量 4 倍,可能超时
把 d_model 从 64 加到 256⚠️ 内存和计算翻倍
更精巧的特征工程✅ 延迟开销小
改进 ns_groups.json✅ 不影响推理速度

→ 那些不显著增加推理时间的改动,是性价比最高的方向。

叁 · Sub-Section III

评估方式

How "winning" is defined: AUC + Latency

这一节回答:比赛怎么判断输赢?谁才算"做得好"?

① 主指标:AUC of ROC

缩写AUC = Area Under the Curve(曲线下面积)
ROC = Receiver Operating Characteristic
口诀"模型把'会点的人'排在'不会点的人'前面"的能力

用一对样本理解 AUC

AUC 在问的核心问题:

"随机抽一对样本,一个真实 label=1,一个 label=0,模型给 label=1 那个的概率更高的可能性有多大?"

假设有 10 条样本(5 正 5 负),配对后看模型有没有"排对":

样本真实 label模型预测
#11(点了)0.92 ✅
#30(没点)0.81
#610.43 ❌(被 #3 排在了后面)
#1000.05 ✅

所有"正负配对"中"模型把正样本排得更高"的比例 = AUC。

三个特殊值,记住它们

0.0
反向完美
0.5
随机猜
1.0
完美

为什么用 AUC,不用准确率?

CTR 数据极度不平衡:真实点击率只有 1%~5%,正负样本比例约 1:30~1:100。

在这种数据上,一个"全部预测不点击"的作弊模型也能拿 95%+ 准确率——但它实际毫无用处,AUC 会立刻揭穿它(=0.5,等于随机猜)。

CTR 预测的关键不是"对/错",而是"排序"——把最可能点的人排在前面。AUC 衡量的就是排序能力,所以是这类任务的金标准。

AUC 提升的"零点零零几"算多吗?

提升幅度意义
+0.001可以接受(已经能写论文)
+0.005不错的改进
+0.01显著改进(论文里大书特书)
+0.05极其罕见(可能是搞错了)

→ 不要被小数点吓到。CTR 任务里 0.001 的提升对应每年多赚几千万——这就是工程师为它拼命的原因。

② 硬约束:推理延迟限制

软约束 · 不达标会扣分,但还能参赛(例:"希望模型不要太大")

硬约束 · 不达标直接淘汰(例:"超过延迟预算的提交直接作废")

延迟限制是硬约束——即使 AUC 全场最高,只要慢了 1 ms,整个提交作废,等于没参加。

"动态公布"是什么意思

  • 腾讯没有事先告诉具体数字,会在比赛过程中根据情况调整
  • 防止参赛者针对固定数字过拟合(把延迟刚好压到 19.9 ms 应付 20 ms 限制)
  • 根据硬件实测动态调整,保证公平

Report 怎么写延迟?(实用 tip)

✅ "Our model achieves X AUC subject to the
    official latency constraint."
   ← 用条件式语言,数字变了不尴尬

❌ "Our model has 17.3 ms latency, well within
    the 20 ms budget."
   ← 写死数字,数字一变就过时

③ 两个机制合起来 = "赢"的标准

                 ┌────────────────────┐
所有提交  ────► │  Step 1:延迟检查  │  ── 超时 ──► ❌ 直接作废
                 └─────────┬──────────┘
                           │ 通过
                           ↓
                 ┌────────────────────┐
                 │  Step 2:AUC 评分  │  ── 越高越好
                 └─────────┬──────────┘
                           ↓
                       排行榜名次

→ 延迟是入场券,AUC 是分数。两关都过才有意义。

自检四问

能答出下面 4 题,说明这一站的内容都消化了。

Q1 为什么 CTR 任务里"全部预测不点击"的模型能拿很高的准确率?

因为 CTR 数据极度不平衡——真实点击率只有 1%~5%。如果有 100 条样本里只有 3 条是点击,一个全部预测"不点击"的模型也能拿 97% 准确率。

但这个模型完全没用——它从不识别真正会点的人。AUC 会立刻揭穿它(=0.5),因为 AUC 衡量的是"把正样本排在负样本前面"的能力,跟具体阈值无关。

Q2 为什么 4 个建模难点里,"推理延迟"和其他三个性质不一样?

前 3 个难点(稀疏、长序列、融合)都是"模型设计层面的挑战"——你可以用更精巧的算法解决。

但推理延迟是"硬性的工程约束"——它不是"难做",而是"做了也作废"。它实际上给你们做改进时立了一个边界:不能为了 AUC 无脑堆参数,所有改动都要在延迟预算内。

所以延迟既出现在 Sub 2 的"难点"里,也出现在 Sub 3 的"评估方式"里——它两者兼具。

Q3 "两类模型融合"这件事,为什么 15 年都没解决?

不是没人做过,也不是缺论文——两条进化树都各自繁衍了 15 年,有几十篇代表作。

难的是:

  • 设计哲学冲突(浅融合无法捕捉跨模式洞察)
  • 训练目标对不齐(对比学习 vs BCE)
  • scaling 行为不同(各自变大都饱和)
  • 工程实现复杂(两套计算图)

需要的不是"再加一个新模型",而是设计哲学层面的统一架构——这就是 PCVRHyFormer 想做的。

Q4 如果你写 report 的 Introduction,要怎么开头?

大致结构(这是 NeurIPS 论文的标准套路):

  • 第 1 段:背景——推荐系统两条技术路线,15 年独立繁衍
  • 第 2 段:问题——4 个工业痛点(浅融合 / 目标不一 / 难 scale / 难运维)
  • 第 3 段:已有工作 + 它们的不足
  • 第 4 段:本文贡献——"我们提出 X,在 baseline 上做了 A、B、C 三个改进,实验证明..."(3-4 个 bullet)

前 2 段几乎全部从 Sub 1 来;第 3 段从 Sub 2 的难点 + Related Work 来;第 4 段需要等队友的实验结果。
