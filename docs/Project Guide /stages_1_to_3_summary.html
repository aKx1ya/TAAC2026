1
Stage One

项目身份 · The Project

回答的核心问题:我是谁?在做什么?交付什么?

核心概念

Baseline 的双重角色

起点(脚手架):腾讯写好的现成方案,代码、模型、训练流程全部打包好,我们不需要从白纸开始。

对照组(参照系):所有改动都要拿原始版本来对比 ——「baseline AUC 0.78,改完 0.81」,这 +0.03 才是我们的贡献。

核心概念

"改良者"角色定位

我们不是模型发明家,是找问题再补救的诊断师。每一个改动都需要:

Motivation(为什么改)+ Evidence(改了有效吗,用 ablation 证明)。

没有 motivation 的改动 = trial-and-error,审稿人不买账。

背景认知

主要矛盾在哪

过去 15 年,推荐系统沿两条独立路线发展:

· 特征交互模型(DeepFM 系)— 擅长静态属性

· 序列模型(SASRec 系)— 擅长行为时间线

不是没人做过,而是"融合"这件事本身真的难。

实操含义

报告(交付物)

形式:9 页 NeurIPS 风格 report

截止:5 月 9 日 ⚠️

核心要求:必须诚实标注哪些是 baseline、哪些是我们的

关键认知:课程分数 ≠ 比赛排名。AUC 不高也能拿高分,关键是 report 写得清晰。

2
Stage Two

问题定义 · The Problem

回答的核心问题:具体在解决什么?怎么算成功?

背景

4 个工业痛点(为什么有比赛)

1 · 跨范式交互浅 — 两类模型只是简单拼接,没真正交流

2 · 优化目标不一致 — 对比学习 vs BCE,各自方向不同

3 · 扩展性受限 — 反 Scaling Law(下面专讲)

4 · 硬件复杂度高 — 两套部署,运维很贵

定义

CTR 预测 = 二分类

给定用户 + 候选广告 + 4 个域的行为序列,输出 [0, 1] 之间的概率,代表"会不会点击"。

不直接输出 0/1 是为了支持排序 — 系统按概率排序,把最可能点的人排前面。

建模难点

4 个建模难点

1 · 稀疏高维 — 用户 ID 上亿,one-hot 不可行,用 embedding 也会爆显存

2 · 长 + 异构序列 — 几百到几千条,4 个域性质完全不同

3 · 静态-序列融合 — 浅拼接信息损失大

4 · 推理延迟 — < 20 ms,不能无脑堆参数

⭐ 重点

Scaling Law 的暗示

LLM 有,推荐系统没有:GPT 系列从 1.5 亿涨到万亿能力质变;DeepFM 维度从 16 到 8192 反而下降。

原因:语言任务有无穷复杂度,推荐任务的匹配模式相对简单,模型很快学完了。

比赛暗示:腾讯希望参赛者找到"让推荐系统也能 scale"的新架构 — 这是个开放性挑战 + 加分项。

评估

AUC 是金标准 · 不是准确率

AUC 衡量的是"排序能力":模型把会点的人排在不会点的人前面的概率。

为什么不用准确率:CTR 数据极度不平衡(点击率 1%~5%),"全部预测不点击"的作弊模型也能拿 95%+ 准确率,但 AUC 立刻揭穿(=0.5,等于随机猜)。

提升幅度:+0.001 已能写论文,+0.01 是显著改进。

硬约束

延迟约束 = 入场券

软约束不达标只扣分;硬约束不达标直接淘汰。延迟是硬约束 — AUC 全场最高也没用。

这是改进 baseline 的"指南针":不显著增加推理时间的改动是性价比最高的方向(改特征分组、时间桶、训练策略)。

Stage Three

数据形态 · The Data

回答的核心问题:输入材料具体长什么样?

事实层

规模与来源

来源:腾讯广告真实日志(real-world logs,不是合成数据)

规模:学术赛道 100 万样本(单卡 GPU 一天能跑完)

状态:完全脱敏 — 所有 ID 都是匿名整数,所有数值都是抽象 float

结构:120 列扁平(flat)布局,不嵌套

结构层

120 列分 6 大类

· ID & Label 5 列(元数据 + 答案)

· User Int 46 列(35 标量 + 11 多值)

· User Dense 10 列(2 预训练 + 8 对齐)⭐

· Item Int 14 列(13 标量 + 1 多值)

· Item Dense 0 列(空 — contribution 空间)

· Domain Sequence 45 列(4 个域,主战场)

⭐ 重点

(key, value) 对齐结构

User Dense 中 8 列与 User Int 同 fid 的列逐元素对齐:

user_int_feats_62: [1, 2, 3] 是类目 ID

user_dense_feats_62: [10.5, 20, 15.5] 是对应统计量

腾讯官方说明:dense 值代表 dwell time / score / probability。这种"用 dense 给 sparse 加权"的思路,值得在 report 里点出。

分布

4 个行为域

Domain A:domain_a_seq_{38–46},9 列

Domain B:domain_b_seq_{67–79, 88},14 列

Domain C:domain_c_seq_{27–37, 47},12 列

Domain D:domain_d_seq_{17–26},10 列

具体业务含义腾讯没明说,这是有意的 — 让方法对未知语义的多域数据都适用。

机制

时间桶机制(time bucketization)

Unix 时间戳直接喂模型不行(数值范围乱)。腾讯 baseline 把"两次行为之间的时间差"分成 65 个桶,边界从 5 秒到 1 年。

每个桶可以学一个 embedding,语义化"刚刚"和"很久以前"。

这是可调参数 — 改 BUCKET_BOUNDARIES 是低成本高潜力的改进方向。

陷阱警示

两种数据格式 · 别混淆

Demo 格式(7 列嵌套 struct)— Hugging Face TAAC2026/data_sample_1000,本地调试用

正式格式(120 列扁平)— 真实训练用

同一份数据的两种打包方式。陷阱:在 Demo 上写完的代码,切到正式数据时可能因格式不同而读不进去。

深度专题 · 团队最关注的难点

4 个 Domain 为什么"非常难处理"

这一节来自和技术组同学的对话沉淀。"难"不是单一问题,而是四层难度叠加。前两层 baseline 已在处理,后两层是我们的 contribution 空间。

第 1 层

异构性 · Heterogeneity

4 个域来自不同业务场景,行为频率、含义、字段都不同。不能粗暴混在一起,也不能用同一个 Transformer 抹平差异。

第 2 层

长序列 · Long Sequence

C/D 域最大 512,A/B 域 256。Self-attention 复杂度 O(L²),序列翻倍计算 4 倍。和延迟约束直接打架。

第 3 层

域间关联未知 · ID Sharing?

Domain A 里的 item_id=1001 和 Domain B 里的 item_id=1001 是不是同一个商品?腾讯没说。需要自己探查(看 baseline 用几个 embedding 表 / 看 ID 范围重叠率)。

第 4 层

时间对齐 · Cross-Domain Time

每个域内时间顺序保留,但4 个域之间的时间交错关系("B 搜 → A 曝光 → B 再搜")baseline 默认丢失。这是潜在的创新方向。

三个边界 · 已知 / 未知 / 待做

✅ 已知
  • 4 个域,共 45 列
  • 每域列名编号(38-46 等)
  • 所有列都是 list<int64>
  • 域内多列逐元素对齐
  • 每位置 i 指代同一次行为
❓ 未知
  • 每域具体业务含义
  • 哪一列是 item_id / category
  • 不同域的 ID 是否共享
  • 每用户的序列长度分布
  • 跨域时间交错关系
🛠️ 需做
  • EDA:ID 重叠率分析
  • 看 baseline 几个 embedding 表
  • 序列长度分布探查
  • 设计跨域融合机制
  • 时间桶可能的优化
学习轨迹 · 我修正过的理解

几次重要的认知校正

这些是我在和 Claude 对话中走过的弯路 + 校正后的正确理解。保留下来给团队成员看,可以避开同样的坑。

⟲
Correction · 校正 1
"图 1 是 Feature Interaction 的数据,图 2 是 Sequential 的数据"— 这是个潜在误解
展开
校正前

认为静态数据(46+10+14)是给 Feature Interaction Models 用的,序列数据(45)是给 Sequential Models 用的 — 两类数据各自给不同模型。

校正后

120 列是同一份完整数据,里面同时包含两类信息。融合发生在模型内部(PCVRHyFormer 内部),不是数据层面。否则就是浅融合(❌),正是要超越的对象。

这一点不校正,后面看 PCVRHyFormer 的 forward 流程时会困惑:"为什么静态和序列从一开始就在交叉?"

⟲
Correction · 校正 2
"100 万样本 = 100 万个用户"— 这是个量级理解错误
展开
校正前

把 100 万样本理解成"100 万个不同的人"。

校正后

100 万样本 = 100 万次"曝光记录"。同一个人可以出现多次,因为他被展示过多次广告。背后真实人数少于 100 万,可能只有几十万。

关键认知:每条样本都有精确时间戳,所以同一用户在不同样本中,他的"过去行为序列截止点"也不同 — 这给了模型时序学习的可能。

⟲
Correction · 校正 3
"评估方式" = "数据集划分"— 这是两件事
展开
校正前

把"评估方式"理解成"训练集 / 验证集 / 测试集划分"。

校正后

这是两件独立的事:数据划分是"在哪里打分"(所有 ML 项目通用);评估方式是"怎么打分"(用 AUC 还是准确率)。Stage 2 第三节讲的是后者。

⟲
Correction · 校正 4
"字段名是猜的"— 公开和未知的边界搞混了
展开
校正前

因为数据脱敏,以为连 user_id、timestamp 这种字段名都是猜出来的。

校正后

分清两层:字段名 / schema 是公开的(写在 algo_qq_com.pdf 里);字段背后的真实业务含义是脱敏的(user_id=87234691 对应谁不知道)。骨架公开,血肉隐藏。

实操影响:讨论时分清"这是关于结构 / 类型 / 名称吗?"(确定的)还是"这是关于业务含义吗?"(推测的)。

⟲
Correction · 校正 5
"锦上添花"— 这个比喻有偏差
展开
校正前

"我们做的是在 baseline 上锦上添花的工作"— 隐含"原作品已经完美,我加点漂亮"的感觉。

校正后

更准的比喻:"诊断病灶"。Baseline 有具体缺陷(浅融合、scaling 差、长序列差),我们的改动是有针对性的修复,不是装饰。Report 的 motivation 必须是"我们发现 baseline 有 X 缺陷"。

给团队成员的 5 分钟 onboarding

如果你是第一次接触这个 project,按下面顺序看就够了

1

先读"30 秒电梯演讲"(本页顶部)

30 秒搞清楚我们参加的是什么、要解决什么、交付什么。这是和外人讲清楚项目的"标准模板"。

2

看大局观图 + 三个 Stage 概览

用 1 分钟看完三个 Stage 卡片 + 中间的 mind-map。建立"故事弧线":两类模型融合不好 → CTR 任务定义 → 数据形态。

3

挑你最关心的 Stage 深读

负责模型?重点看 Stage 1 + Stage 2 难点。负责数据?重点看 Stage 3 + 4-Domain 专题。负责报告?整篇都要扫一遍。

4

看"5 次认知校正"避坑

这是同伴踩过的具体错误 + 校正版理解。不读这部分会重复同样的弯路。

5

读 4-Domain 专题

这是整个 project 最难的技术点。哪怕你不直接处理这部分,也要懂它的难度结构,才能在团队讨论中跟上节奏。

6

记住"延迟约束 = 指南针"

无论你做哪部分改进,都要在脑子里挂着这条线:不增加推理时间的改动 = 性价比最高。这是贯穿整个 project 的设计准则。
