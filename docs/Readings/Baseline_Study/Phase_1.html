1.1

数据的全貌与分类逻辑

120 列不是拍脑袋分的 — schema.json 是"数据说明书"
五个盘子，schema.json 照章办事核心概念
专业表述：120 列按 schema.json 登记类型分为 user_int / user_dense / item_int / item_dense / seq 五大类，这是数据说明书提前定义好的
分类不是我们主观拍脑袋决定的。数据提供方（腾讯广告）在交付 Parquet 文件的同时，附带了 schema.json 这本"花名册"。它明确定义了：哪些列是 int 类型（离散 ID，做 Embedding 查表）、哪些是 dense 类型（连续数值，直接投影）、哪些是 seq 类型（行为序列，走 Transformer 编码）。user 侧（谁在看）和 item 侧（看的是哪个广告）天然分开，因为模型内部是双塔结构。
FeatureSchema — 门牌号管理器代码设计
专业表述：FeatureSchema 维护 (feature_id, offset, length) 三元组，将扁平化的特征向量映射回各个 feature 的位置区间
所有 int 特征拼成一根长向量后，模型需要知道"第 7 号特征从第几位开始、占几位"。FeatureSchema 就是这本门牌册：fid=7, offset=1, length=3 意味着从第 1 位开始取 3 个值。没有它，模型拿到一串数字也不知道谁是谁。
item_dense = 0：空白 = 机会改进方向
专业表述：item_dense_dim = 0，模型对物品侧的表征完全依赖离散 Embedding，缺少统计先验
广告侧没有任何连续特征——模型只能靠 14 个 ID 的 Embedding 来理解广告，缺乏"这个广告出现过多少次""历史点击率多少"等统计信号。这是一个明确的改进方向：可以人工构造 item 频次、CTR 等统计特征填进这个空盘子。
关键澄清

dataset.py 做的不是"降维"（把 100 个压成 10 个），而是"分类整理 + 格式转换"——食材没变少，只是从散装变成了摆好盘的状态。真正的降维和特征交互发生在 model.py 里。

1.2

序列处理：截断、填充与妥协

截断点不是"最优解"，而是"数据分布 + 计算成本"的折中
截断 + 填充 = "统一试卷长度"核心概念
专业表述：variable-length sequences are truncated to max_len and zero-padded, with padding mask provided for attention
太长了 → 砍掉最早的。超过 max_len 的部分直接丢弃（保留最近的）。太短了 → 补零。不够的位置填 0。模型通过 seq_len 知道每个用户的"真实答题数"，不会把补零的位置当真。就像考试：试卷 256 题，你做了 30 题，剩下空着，老师知道只改前 30 题。
截断点凭什么定在 256 / 512？深层追问
专业表述：seq_max_lens 的值来自数据分布（95%+ 用户的行为序列长度）与 Transformer O(L²) 复杂度的工程权衡
不存在数学上的"最优截断点"。它是一个工程取舍：

• 数据分布：95%+ 的用户行为序列长度 < 200，设 256 只影响极少数重度用户的早期行为
• 计算成本：Transformer self-attention 是 O(L²)，L=512 的算力是 L=256 的 4 倍
• 收益递减：从 256 提到 512 可能只多覆盖 3% 的用户，提到 1024 不到 1%
• 信号衰减：广告点击场景中，最近 256 次行为已覆盖数天到数周，更早的行为对当前预测贡献极小
截断会丢信息，但影响很小关键洞察
专业表述：truncation 丢弃长尾用户的早期行为，但实际影响被稀释——频域 a/b 行为稀疏、频域 c/d 记录低频事件
丢掉的是极少数重度用户的最早期行为，不是随机的。这部分行为时间久远、信号衰减严重，在点击率预测任务中的边际贡献很低。如果换一个场景（比如金融风控需要回溯一年），截断点就需要重新评估。
概念上的妥协

Padding（补零）引入的是假信息——模型得额外学一个 mask 机制来忽略这些零。"老师，空着的题你别改。"
Truncation（截断）丢掉的是真信息——重度用户最早期的行为被舍弃了。
这两个操作和业务逻辑毫无关系，纯粹是为了让矩阵乘法能跑在 GPU 上。在深度学习领域，这是一个普遍存在但少有人挑明的真相。

一个用户的 domain_a 序列处理全流程
原始 800 条浏览 → 截断到 256 → 多列对齐 × 256 → 时间桶化 → 3 个张量输出
1.3

DataLoader：打包与分发

训练/验证切分 · Shuffle Buffer · 成品直送
前后切分，不是随机抽取核心概念
专业表述：按 Row Group 顺序，前 90% 为 train split，后 10% 为 validation split，等效于 temporal split 避免 data leakage
valid_ratio=0.1 = 留最后 10% 的数据块做验证。不是随机抽，而是"前 90% 练习、后 10% 模拟考"。因为文件按时间排序，这等于"用历史学习、用最近验证"——避免了"用未来数据预测过去"的作弊问题。
Shuffle Buffer — 传送带上的搅拌池核心概念
专业表述：IterableDataset 用 buffer_batches=20 实现局部随机化，在 20×256=5120 行范围内行级打乱
数据太大不能全部加载打乱。解决方案：在传送带中间放一个能装 20 箱的水池。攒满 20 个 batch（5120 条）→ 在池子里搅乱 → 重新切成 20 箱送出。不是完美的全局打乱，但足以破坏原始的时间顺序，让模型不会"记住数据排列"。
无 collate_fn — 成品直送代码设计
专业表述：DataLoader(batch_size=None) 透传 IterableDataset yield 的已成型 batch dict，不调用 default_collate
通常的流程：一条一条取 → 用 collate_fn 拼成一批。但这个代码反过来了——dataset 自己直接产出成品 batch。DataLoader 设 batch_size=None，只负责传菜不摆盘。预分配 buffer 复用，避免反复拼接张量的开销。
完整数据分发流程
Parquet RecordBatch → _convert_batch() 转张量 → Shuffle Buffer ×20 → DataLoader 透传 → 训练循环
1.4

三步总结：主要矛盾与次要矛盾

理解什么是对数据的理解，什么是对硬件的妥协
主要矛盾框架
真实数据的非结构化特征 vs GPU 计算要求的规整矩阵
Phase 1 的全部工作都在解决这个矛盾。三个子步骤各司其职：
第一步：分类 — 数据驱动语义理解 → 工程分派
schema.json 怎么定义，代码就怎么分。user 走 user 塔，item 走 item 塔，int 查 Embedding，dense 直接投影，seq 走 Transformer。
这一步是数据驱动的——不是主观划分，而是根据数据本身的性质和推荐系统的固有结构做出的必然选择。
第二步：对齐 — 硬件妥协对硬件的妥协，不是对数据的理解
截断丢掉真信息（重度用户的早期行为），补零引入假信息（模型要额外学 mask 来忽略）。
这一步和业务逻辑毫无关系——纯粹是为了让矩阵乘法能跑在 GPU 上。截断点不是数学最优解，而是"数据分布 + 计算成本 + 工程经验"的三方折中。
第三步：打包 — 效率工程效率工程
256 条一组 + Shuffle Buffer 局部打乱 + DataLoader 透传，让训练循环能以最高吞吐量运转。
为什么是 256？显存限制。为什么打乱 20 批？够破坏时间顺序就好，不用完美打乱。为什么不用 collate_fn？预分配 buffer 复用，避免反复拼接。
智力活在哪里？关键判断
真正理解数据语义、做特征交互、非线性变换——那些"智力活"——都在 Phase 2 的 model.py 里。
Phase 1 解决的是"数据能不能被 GPU 处理"的问题，不是"数据有没有被理解"的问题。理解数据、从数据中提取模式，是模型的责任，不是数据加载器的责任。
三步流水线全景
100万条 × 120列
参差不齐 → ① 分类
schema 照章 → ② 对齐
截断 + 补零 → ③ 打包
256/batch → model.py

Phase 1 检查点 — 已理解

你现在能用自己的话说出：dataset.py 的三步本质是 ① 分类（schema.json 照章办事，告诉模型数据该走哪条路）→ ② 对齐（解决"现实参差 vs GPU 要整齐"的矛盾，是概念上对硬件的妥协）→ ③ 打包（256 条一批，Shuffle Buffer 搅乱，DataLoader 透传）。你知道截断点不是数学最优解，补零和截断都跟业务逻辑无关。你区分了"数据准备工作"和"理解数据的智力活"——前者在这里，后者在 model.py。
