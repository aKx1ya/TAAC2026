章 · 01

我们到底在做什么？

本质上，整个项目就是在训练一个"算命先生" —— 给它看一个用户和一条广告，让它预测"这个用户会不会点击这条广告"。

这是一个二分类问题（Binary Classification）：输出要么是"会点"（1），要么是"不会点"（0）。但模型不会直接给出 0 或 1，而是给出一个 0 到 1 之间的概率值，比如 0.73 表示"73% 的概率会点击"。

评估这个"算命先生"准不准的指标叫 AUC（Area Under Curve）。AUC = 0.5 意味着瞎猜，AUC = 1.0 是完美预测。我们的 baseline v0.1 跑出了 AUC = 0.8067，比 HyFormer 官方 baseline（0.7952）要好。这是我们的起点。

类比 · Analogy

把这个模型想象成一个相亲网站的推荐算法：用户画像（喜好、年龄、历史浏览）+ 候选对象（这条广告的属性）→ 预测匹配度。我们要做的就是让这个推荐越来越准。

输入是什么？

数据集有 120 列，分成几大类：

• 用户特征（约 56 列）：用户 ID、年龄段、设备类型、行为偏好等
• 广告特征（约 14 列）：广告 ID、广告类型、所属品类等
• 4 个行为序列（45 列）：用户最近的点击、浏览、收藏等历史行为
• 标签（1 列）：用户最终是否点击了这条广告

输出是什么？

对每一对（用户, 广告），输出一个 0.0 ~ 1.0 的点击概率。整个比赛的目标，就是让这个概率尽可能贴近真实情况。

代码的流水线全貌

想象一条工厂流水线：原料（数据）从一端进入，经过几个加工站，最终变成产品（预测概率）。每个文件就是流水线上的一个工位。

整个流程被 train.py 这个"总指挥"调度起来，配置参数从 run.sh 这个"启动按钮"传入。流程跑完一遍叫一个 step，跑完所有数据一遍叫一个 epoch。模型就是在一遍又一遍的"看数据 → 预测 → 算错误 → 调整"中越来越准。

类比 · Analogy

就像学生做练习题：看题（数据） → 写答案（预测） → 对答案（计算损失） → 错的地方修正思路（更新权重）。重复几万次后，水平就上去了。

章 · 03

八个文件，逐个拆解

现在我们一个一个看 Interformer/v0.1/ 里的文件，知道每个是干嘛的、有多重要、要不要改。

核心架构 · 改它就是改模型
配置参数 · 经常调
辅助工具 · 偶尔改
评估推理 · 几乎不改
model.py
核心 · 必改
模型的"大脑" —— 定义网络长什么样

这是整个项目最重要的文件。它定义了 PCVRInterFormer 这个神经网络的结构 —— 有多少层、每层是什么、信号怎么流动。InterFormer 架构包含三个模块：

• Interaction Arch · 处理非序列特征之间的交互
• Sequence Arch · 编码 4 个行为序列
• Cross Arch · 让上面两个模块互相"对话"，最后输出预测

什么时候改它？任何关于"模型结构"的改进 —— 加新层、改注意力机制、加 DCN、加 RoPE，全在这里改。这是 v0.2 主要要动的文件。
dataset.py
核心 · 可能要改
数据搬运工 —— 把硬盘上的 Parquet 文件读成模型能吃的格式

原始数据是几个大的 .parquet 文件（一种高效的列式数据格式）。这个文件负责：

• 一批一批地读取数据（batch）
• 把变长的行为序列填充到固定长度
• 把时间戳转换成时间桶（time bucket）
• 处理缺失值和越界值

什么时候改它？当你要做特征工程时 —— 比如背景文档提到的"item log-frequency"、"Bayesian CTR" 这类新特征，需要在这里构造。
train.py
配置 · 经常改
训练总指挥 —— 接收命令行参数，把所有东西串起来

这个文件本身代码不多，但它是入口。它做三件事：

• 解析参数（argparse）：你在 run.sh 里写的所有 --xxx 参数都在这里被读取
• 构建模型：把参数喂给 model.py 里的 PCVRInterFormer
• 启动训练：把模型交给 trainer.py

什么时候改它？当你想加新的命令行参数时（比如新的超参数、新的开关）。日常调参一般不动它，只改 run.sh。
trainer.py
核心 · 训练逻辑
训练循环本身 —— 真正"在训练"的地方

这是模型变聪明的引擎。每一个 step 都在这里发生：

• 取一个 batch 的数据 → 模型预测 → 计算损失 → 反向传播 → 更新参数
• 每隔一段时间做一次 validation（在没见过的数据上测准确率）
• 维护 EarlyStopping（验证集 5 轮没进步就停）
• 管理 双优化器（Embedding 用 Adagrad，其他用 AdamW）

什么时候改它？当你想加新的训练技巧时 —— GradScaler（混合精度）、学习率 warmup、cosine annealing、梯度累积、修复 GAUC 计算等。
utils.py
辅助 · 偶尔改
工具箱 —— 日志、随机种子、损失函数、早停机制

这个文件里都是"小工具"，被其他文件反复调用：

• create_logger：打日志
• set_seed：固定随机数，让实验可复现
• EarlyStopping：早停 + 保存最佳模型
• sigmoid_focal_loss：Focal Loss（处理类别不平衡的损失函数）

什么时候改它？想加新的损失函数（比如 weighted BCE）、改早停策略时。架构层面的改动很少涉及这里。
run.sh
配置 · 日常调参
启动按钮 —— 一行命令开始训练

这是一个 shell 脚本，本质上就是把所有超参数打包成一个 python3 train.py --xxx --yyy 命令。它写了：

用什么 tokenizer、几个 token、batch 大小是多少、用几个 worker 加载数据等。日常调参就是改这里。

什么时候改它？调超参数（学习率、batch size、d_model 等），切换不同配置时。这是你最常打开的文件之一。
ns_groups.json
配置 · 偶尔改
特征分组规则 —— 把 120 列特征语义上归类

v0.1 用的是 rankmixer 模式，这个文件其实不生效（看 run.sh 里 --ns_groups_json ""）。但如果你切换到 group 模式，这个文件会告诉模型"哪些特征算同一组"，可以减少参数量、做更细的建模。

什么时候改它？探索 group tokenizer 模式时；做特征工程加入新分组时。
schema.json
数据 · 不改
数据集的"说明书" —— 告诉代码 120 列分别是什么

这是由数据提供方生成的元数据文件，描述每列的名字、数据类型、词表大小（vocab size）等。你不应该手动改它，否则代码会和数据对不上。

什么时候改它？除非数据格式变了，否则永远不改。
infer.py
推理 · 几乎不改
最终提交脚本 —— 训练完，用它生成提交结果

训练好的模型保存在 checkpoint 里。比赛要提交的是模型对测试集的预测结果。这个文件负责加载训练好的模型、读测试数据、跑预测、把结果写成 predictions.json。

什么时候改它？当你改了 model.py 的结构时，可能需要同步修改这里的模型构建逻辑，但日常训练不动它。
章 · 04

想改进模型？改哪里？

这是一份决策矩阵：你想做什么样的改进，对应该改哪些文件。把它当成一张作战地图。

你想做的改进
需要改的文件
新增模型结构（加 DCN、改注意力、加 RoPE）
model.py
特征工程（构造新特征如 item 频次、Bayesian CTR）
dataset.py + 有时 model.py
训练技巧（warmup、GradScaler、cosine LR）
trainer.py + train.py（加参数）
换损失函数（Focal、weighted BCE）
utils.py + trainer.py
调超参（lr、batch size、d_model）
run.sh（只改这一个）
修 v0.1 已知 bug
model.py + trainer.py
改提交格式
infer.py

一个重要的工作流原则：一次只改一个变量。如果你同时改了模型结构、损失函数、batch size，效果变好或变坏你都不知道是哪个因素导致的 —— 这正是 v0.3 失败的原因。

章 · 05

三个已知的 Bug

v0.1 baseline 跑出了 0.8067 的 AUC，但这是带着三个 bug 跑出来的。修了它们，理论上还能再涨。

Bug · 01 · Critical
model.py 第 480 行 · seq_encoder_type 被静默删除

在 PCVRInterFormer.__init__ 中，参数 seq_encoder_type 被 del 掉了。这意味着无论你在 run.sh 里写 --seq_encoder_type swiglu 还是 longer，代码都只会用默认的 transformer。

影响：v0.1 用的就是 transformer，所以暂时没事。但要尝试其他 encoder 必须先修这个 bug。

Bug · 02 · Critical
reinit_high_cardinality_params 的逻辑反转

当 cardinality_threshold=0（默认意为"永不重置"）时，条件 num_embeddings - 1 <= 0 对几乎所有 embedding 都成立 → 反而把所有 embedding 全重置了。这是 v0.5 训练 AUC 突然崩盘的元凶。

影响：v0.1 因为 reinit_sparse_after_epoch=1 但训练通常在 epoch 1 之前就 early stop 了，所以没触发。一旦训得久了就会爆炸。

Bug · 03 · Medium
GAUC 计算硬编码为 0

GAUC（Group AUC，按用户分组的 AUC）能反映模型对每个用户的个性化预测能力。但 trainer.py 里这个值是硬编码的占位符，所有训练日志里的 GAUC 都是无效的。

影响：无法评估个性化效果。背景文档提到"即使 AUC 0.852 时 GAUC 仍接近 0"，说明特征表示是瓶颈 —— 但首先要把 GAUC 修好才能确认这个判断。

章 · 06

接下来怎么走？

现在你已经理解了整个代码库的结构和职责。下面是一个建议的行动顺序，从最简单到最有冲击力：

  1. 在 Claude Code 里读一遍代码。让 Claude Code 把每个文件都解释一遍。这是你"以读促写"的方式，遇到看不懂的代码片段直接问它。
  2. 跑通 v0.1 baseline。在 GPU 服务器上跑一次完整训练，确认你能复现 0.8067 这个 AUC。这是后续所有改进的对照基线。
  3. 修三个 bug → 创建 v0.2。把 v0.1 整个目录复制成 v0.2，只修 bug 不改架构，再跑一次。看看修了 bug 之后 AUC 是涨还是稳定。
  4. 做一次小特征工程实验。在 dataset.py 加 item log-frequency 特征（背景文档建议的 +0.003~0.008 AUC），创建 v0.3。
  5. 有了节奏后再做大动作。架构改动（DHEN、DCN、RoPE）放到 v0.4+，因为这些需要同时改 model.py 和 trainer.py，复杂度高。

每一步都遵循一个铁律：一次只改一个变量，每个改动都和上一版严格对比。
